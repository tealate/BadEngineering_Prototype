# BadEngineering

Unity 6で開発するゲームプロジェクト。

## Project Goal

PvE協力型アクションゲーム。

プレイヤーは車両の任意位置に武器を取り付け、
重量・重心・反動による物理挙動を楽しむ。

現在はPrototype段階。

## Development Policy

- Unity 6を使用
- C#を使用
- 可能な限りシンプルな実装を優先
- Prototype段階でも、機能追加や仕様変更に対応しやすい拡張性・保守性を優先する
- 将来使うか分からない仕組みを先回りして作らず、現在想定できる変更点に対して拡張しやすく設計する
- 過剰な抽象化を避ける
- Rigidbodyを利用した物理挙動を優先
- 既存コードを変更する場合は影響範囲を確認する
- 調査・ツール呼び出し・説明は作業に必要な範囲に絞る
- 応答は結論中心で簡潔にする

## Code Readability

Codexが新規作成・変更するコードは、第三者が処理の目的と流れを追えることを優先する。

- クラス、メソッド、変数には、役割が具体的に分かる名前を付ける。意味の曖昧な略語や `data`、`temp`、`manager` などの汎用名を安易に使わない
- 1つのメソッドには1つの責務を持たせる。処理の段階が複数ある場合や、長くて流れを把握しづらい場合は、目的が分かる名前のメソッドへ分割する
- ネストは浅く保ち、ガード節や早期リターンを使って正常系の処理を追いやすくする
- マジックナンバーや用途不明な文字列を直接埋め込まず、意味の分かる定数または設定値として定義する
- `bool` を引数に複数渡して呼び出し側の意味が不明になる設計を避ける。必要に応じて enum や用途別メソッドを使う
- Unityのライフサイクルメソッド（`Awake`、`Start`、`Update`、`FixedUpdate` など）には処理を詰め込まず、役割ごとのメソッドを呼び出す構成にする
- 変更時は周辺コードの命名・書式に合わせ、無関係なリファクタリングを混ぜない

### Comments

コードだけでは意図や前提を判断しにくい箇所には、日本語のコメントを記載する。

- コメントには「何をしているか」の言い換えではなく、「なぜ必要か」「どの制約があるか」「直感に反する挙動の理由」を書く
- 物理計算、座標変換、Unity固有の実行順序、暫定的な回避策、仕様由来の数値には、その意図を短く説明する
- 複数段階の処理には、必要に応じて処理のまとまりが分かる短いコメントを置く
- 公開APIや使い方が自明でない型・メソッドには XML ドキュメントコメント（`///`）を付ける
- TODOを書く場合は、未対応の内容だけでなく、残している理由または対応条件も記載する
- コードを読めば明白なコメント、実装と同じ内容を繰り返すコメント、更新されていないコメントは追加しない
- 実装を変更した際は関連コメントも更新し、コードとコメントを一致させる

## Current Prototype Scope

1. Player movement
2. Vehicle movement
3. Enter / exit vehicle
4. Weapon pickup
5. Attach weapon to vehicle
6. Fire weapon
7. Apply recoil to vehicle
